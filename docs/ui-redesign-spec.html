五、字体定稿

你的答复是「换一个长得差不多的就行，不要求」——那就不引入任何字体文件，用系统栈，零字节成本、零许可风险、不破坏离线。

定稿：系统字体栈

--font-ui: "Segoe UI Variable Text", "Segoe UI", -apple-system,
           "Microsoft YaHei UI", "Microsoft YaHei", "PingFang SC",
           system-ui, sans-serif;
--font-mono: "Cascadia Mono", "Consolas", "SF Mono", Menlo, monospace;

Windows 上英文落到 Segoe UI、中文落到 微软雅黑。Geist 是几何无衬线，Segoe UI 是人文无衬线——风格不完全一致，但在 12–14px 的界面字号下差异很小，且好处是「中英文都是本机原生的，看起来不违和」。

必须知道的一件事：换来换去都躲不开「中英分属两套字体」。 不管是 Geist、Inter 还是 Segoe UI，都没有中文字形——中文一律回落系统字体。这是字体选型层面无解的， 唯一解法是打包一套「拉丁 + 中文同源」的字族（思源黑体 / MiSans / HarmonyOS Sans SC），代价是 +0.6～2MB， 且主 bundle 已经 4.5MB。所以你这条「不要求」的答复，我认为是这次最省的一个决定。

升级路径留好了：若将来觉得英文不够像设计稿，换 MiSans 或 HarmonyOS Sans SC，改动量 = 改 --font-ui 一个变量 + 加一个 woff2，不用重构。

两处必须单独处理，和选哪个字体无关：

  • Monaco 不吃 CSS 的 font-family。编辑器内部用自己的字体设置，必须显式调 editor.updateOptions({ fontFamily: '...', fontSize: 13 })，否则编辑器里还是默认字体，与外面不一致。
  • 字体不能引 CDN。本项目卖点之一是内网可用，即便将来换了字体也必须本地打包（public/fonts/）。

七、双语切换的落地方案（Q2）

「按语言切换」听起来只是把文字换成另一个语言，但项目里有一处查字典解决不了：识别子系统的提示是运行时动态拼接的。

现状：拼装出来的中文串

detect/index.js 的 describeDetection() 会把模型判断结果拼成完整句子，例如：

未发现任何 TypeScript 专有语法，按 JavaScript 处理（模型判为 TypeScript）

这句话在中文里要靠语序和括号，直接按词替换成英文会立刻散架。

定稿：改成「模板 + 参数」，让文案可翻译

// 检测层只返回结构化结果，不再返回成品句子
{ code:'detect.refine.jsOverTs', params:{ model:'TypeScript', final:'JavaScript' } }

// i18n 层负责措辞
zh: '未发现任何 {model} 专有语法，按 {final} 处理'
en: 'No {model}-specific syntax found — treating as {final}'

这是本次唯一一处需要改检测子系统（src/detect/）内部的地方。好在改动是「把拼接挪走」而非重写逻辑，且现有自检（识别 24/24）能立刻验证改造没改坏判断结果。

i18n 的落点（要动约 40 条字符串）

区域条数示例
顶栏约 4新标签 / New Tab、tagline
工具栏约 8格式化 / Format、压缩 / Compress、自动检测 / Auto Detect、各按钮 title
历史面板约 8历史记录 / History、清空 / Clear、相对时间（分钟前 / min ago）
状态栏约 6就绪 / Ready、大小 / Size、行,列 / Ln,Col
空状态约 5粘贴引导、3 个示例按钮
提示与错误约 11识别 5 种状态、格式化错错、清空确认、长内容提示
代码组织：新增 src/i18n/ 目录，但界面代码仍留在 App.js。 这是刻意贴合项目现有约定的——format/、detect/ 都是「能力子系统独立成目录，UI 集中在 App.js」。 为状态栏、空状态单独建 components/ 目录会打破这个约定，而且这个体量（约 300 行 UI）还不值得拆文件。

语言选择要持久化（localStorage），否则每次刷新都回默认值，用户会烦。 但不要和「识别语言」混用同一个 key——一个是界面语言、一个是内容语言，语义完全不同，混用将来必出 bug。

另外两件本轮刻意不做的（说明理由，避免以后被当成遗漏）

  • handleRemoveEscape 的重写 —— 它的实现（两次正则、不幂等、嵌套转义会错）确实有问题，但重写属于逻辑变更，会稀释本轮「只改界面」的验证边界。建议单独立一项，因为它有现成的自检可挂。
  • 全语言语法校验定位 —— 设计稿里没有这个需求，而成本远高于界面改动（要接各语言服务）。本轮只做 JSON + 格式化错误的定位（Monaco 免费提供）。
