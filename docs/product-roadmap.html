1.2 真正的技术资产（护城河在哪）

  1. 跨语言的「代码整理」能力——竞品几乎清一色只做 JSON 一种格式，我们一次覆盖 11 种，且 C/C++/Java/C#/Python/Go 用的是与本地工具链同源的格式化器（clang-format / Ruff / gofmt），不是自己写的近似实现。这一条别人短期抄不走。
  2. 粘贴即识别——从「先选语言再粘贴」变成「粘完就对了」。规则层可解释（会告诉你判定依据），模型层兜底，还有针对 JS/TS 的语法纠正。这个体验 VS Code 级别才有。
  3. 零外传 + 零后端——没有服务端，数据不出浏览器；部署只是一个 nginx 静态目录。这让它天然适配「代码不能贴到公网工具」的场景。
  4. 可回归的质量基建——自检覆盖了「页面不报错但功能静默失效」这类最难发现的问题（含 App 挂载断言、展示名断言）。多数同类个人项目没有这层。

1.3 现存缺陷与风险（按严重度）

这些是我读代码时确认的、会真实伤害用户的问题，不是风格偏好。

级别问题后果与依据位置
P0 历史记录会静默丢数据 条数无上限、单条大小无上限，localStorage 只有约 5MB 配额。写满后 setItem 抛 QuotaExceededError，代码只 console.error 就过去了——用户不会收到任何提示，只会发现历史记录莫名其妙少了一段。这是"用户辛苦编辑的内容凭空消失"，属于信任级问题。 App.js:59-66
P0 当前编辑内容不落盘 只有点「新页面」才会保存。刷新、误关标签页、断电 → 正在编辑的内容全丢，且没有任何草稿机制。对「粘贴一段 JSON 临时看/改」的核心场景来说，这是最频繁的数据损失路径。 App.js:234-255
P1 没有文件进出通道 不能拖拽打开文件、不能下载/另存、不能一键复制全文。用户拿到一个 .json/.py 文件，得先用别的编辑器打开、全选、复制、再粘进来，出去时反向再来一遍。这是"编辑器"的基本盘缺失。 全文件无实现
P1 没有校验反馈 Monaco 其实已经算出了 JSON 语法错误的行列（诊断信息就在模型里），但界面完全没有暴露。用户压缩失败只会看到一个 alert('Invalid JSON format: ...')，不会定位到第几行第几列。 App.js:189-191
P1 去转义逻辑不幂等、嵌套会错 两次全局正则近似反转义，\\\\" 这类嵌套转义会处理错，且重复点两次结果不同。用户无法预期结果。 App.js:207-215
P2 历史面板无法收起 showHistory 只有初始值 true，没有任何地方能改它——250px 宽度永久占用，小屏/窄窗口下编辑器被挤。 App.js:19
P2 无快捷键 格式化没有快捷键，压缩没有快捷键，保存没有快捷键。工具类产品的重度用户 100% 靠键盘，这块目前是空白。 全文件无实现
P2 命名与能力错配 页面标题、README 都叫 JSON Editor，但实际支持 40 种语言识别、11 种格式化。新用户看到标题不会知道它能处理 Python/Go/Java，自己人也容易低估它的能力边界。 README · App.js:334
P2 「离线可用」名不副实 没有 Service Worker，首次访问仍需连到服务器。"离线"目前只等于"不依赖外网/CDN"，不等于"断网能用"。定位口号比实现大了一步。 无 public/sw.js
P3 零使用数据 没有任何埋点。哪个语言最常用、识别准不准、用户卡在哪一步——全靠猜。所有优先级判断目前都只能是判断而非证据。 全文件无实现
P3 无测试文件 装了整套 testing-library 但零测试。现有自检很能打，但它只覆盖算法与两条 UI 链路，重构类改动（比如引入多标签）缺乏安全网。 全项目无 *.test.js

二、定位：先想清楚这是什么，再决定做什么

2.1 一句话定位（建议）

不联网也能用的多语言代码整理台——粘贴任意代码，自动认出是什么语言，用与本地工具链同源的格式化器整理好；数据一个字节都不出你的电脑，整套东西一个容器就能部署进内网。

这比旧的"Multifunctional JSON Editor"准确，且三个卖点都能被代码兑现：自动认出（detect 子系统）、同源整理（wasm-fmt）、不出电脑（零后端 + 本地打包）。对外名称已定为 peek / 「一瞥」。

2.2 目标用户与核心场景

用户典型场景为什么选我们而不是 jsonformatter.org
内网/受监管环境的开发者
金融、政企、涉密单位		 把一段配置或日志粘到工具里整理，但代码不允许出网 公网工具一律不可用（数据外传）或访问不了（无外网）。我们是唯一能私有化部署的选项
多语言混用的后端 / 全栈开发者
同一个项目里 Java + Python + SQL + JSON		 一天里要整理五六种不同格式的片段，不想为每种语言开一个工具 一个页面覆盖 11 种格式化器，粘贴即识别，不用先在下拉框里找语言
需要临时看代码的运维 / 测试 拿到一段别人给的代码或配置，要快速看懂结构与层级 高亮 + 格式化 + 语言判定一步到位，不需要装任何 IDE
必须承认的数据缺口：以上用户画像是基于「代码里已投入的能力」反推的合理假设，不是用户研究的结论——项目目前零埋点、零访谈。所以本规划的优先级标注为"判断级"而非"证据级"。第四节给出把判断变成证据的最小方案。

2.3 战略分叉（需要你拍板）

方向 A：离线·内网研发工具 建议主攻

面向"代码不能出网"的团队，强化私有部署、零外传、本地一致性。技术选型已经完全站在这一侧（无后端、本地打包、Docker），继续投入是顺势。

代价：用户量天花板低，价值靠"团队内使用深度"而非流量。

方向 B：公网开发者工具站

与 jsonformatter.org / CodeBeautify 正面竞争，靠"多语言 + 无广告 + 隐私"差异化。

代价：红海、需要 SEO 与持续运营，且必须补齐全部及格线功能才有入场资格——投入产出比明显更差。

我的建议：以 A 为主目标，B 作为自然溢出渠道。理由：差异化选择应该顺着已有资产走，而不是逆着走。我们花了力气把 Monaco、wasm 格式化器、模型权重全部本地化——这份投入只有在"离线/内网"场景下才能变现；在公网站点上，用户根本感知不到它，反而会拿我们和功能更全的竞品比长短。

三、下一步功能规划

3.1 四条投资主线

主线要解决的问题成功的样子
L1 不丢数据历史会静默丢、刷新会丢当前内容——信任级缺陷任何一次编辑都不会因为刷新/配额而消失，且用户能看到保存状态
L2 进得来出得去没有文件通道、没有快捷键——"编辑器"基本盘缺失拖一个文件进去就能编辑，一键下载/复制出去，全程可以不用鼠标
L3 看得懂数据没有校验定位、没有转换——JSON 场景的及格线粘贴畸形 JSON 立刻指出第几行错在哪；一键在 JSON/YAML/CSV/TS 类型之间转换
L4 把护城河做宽差异化能力（多语言）覆盖广度还不够，识别低置信时体验生硬YAML/XML/SQL/Markdown 也能格式化；识别拿不准时给出候选让用户一点即改

3.4 Non-goals（明确不做）

明确写下来，防止范围蔓延——尤其要防止"顺手加一个后端"这类会毁掉定位的动作。

不做理由
不做账号体系与云同步"数据零外传"是核心卖点。一旦引入服务端存储，整个定位崩塌，且要背上合规责任
不做分享链接 / 多人协作需要后端与内容托管，与上一条同因；且内网场景下链接分享无意义
不做完整 IDE不加终端、调试器、包管理、多文件项目。我们是"片段整理台"，不是编辑器替代品
不做 AI 生成 / 解释代码与"零外传"直接冲突；本地模型又会拖垮体积与首屏。若要做，必须是可选且默认关闭
不做表单化 / 拖拽式数据建模树视图之后的形态，需求未验证，投入产出比不明
不追求支持所有语言格式化器只补高频的（YAML/XML/SQL/Markdown/TOML）。长尾语言保持"能高亮、按钮置灰"的诚实状态即可

四、怎么知道做对了：度量体系

没有后端，所以指标必须是本地可算、不外传的。这部分本身就是第 13 项（本地埋点）要交付的东西。

层级指标为什么是它
北极星 每周「完成的整理动作」次数
= 格式化成功 + 转换导出 + 校验通过 的合计		 它不是访问量，而是"用户真的把一段代码整理好了"的次数——这正是本产品唯一的价值主张。访问量高但没人格式化成功，等于没价值
驱动指标 粘贴识别命中率（成功切换 ÷ 触发识别） 这是我们的差异化体验，命中率掉到某个阈值以下，护城河就没了
识别未命中时的真实语言分布直接告诉我们该补哪门语言的规则或纠正逻辑——避免凭感觉调参
各语言使用频次分布决定第 9 项（扩展格式化器）的补全顺序，而不是按"哪个语言更知名"来排
导出 / 复制次数衡量"进得来出得去"是否真的被用起来；如果长期为 0，说明第 3 项做错了方向
健康指标 localStorage 写入失败次数 第 1 项的直接验收指标。上线后这个数必须为 0
草稿恢复触发次数衡量第 2 项到底救了多少次数据
未捕获异常数 / 格式化器加载失败率保持现有回归链路（含运行时错误收集）持续为 0

五、需要你拍板的三个决策

#决策点选项与我的建议
1 战略方向选 A 还是 B？ 建议 A（离线·内网工具）。这会决定第 20 项（i18n）是否要提前，以及是否值得为公网 SEO 做任何事。选 A 则本规划直接执行；选 B 需要额外补 Diff、树视图、JSONPath 才能入场
2 「新页面」的破坏性行为要不要改？ 现在是"保存并清空"，是个会劝退新用户的模型。建议先做自动草稿（第 2 项），用两周埋点数据看用户是否真的需要同时开多个文档，再决定第 16 项（多标签）的优先级。不建议现在就直接重构
3 愿不愿意为"证据"多花 1 人日？ 第 13 项（本地埋点）本身不产生用户可见价值，但它是唯一能把"我的判断"变成"数据"的手段。建议做，否则下一轮规划仍然只能靠猜

本规划的假设与边界：① 用户画像与优先级为基于代码资产反推的判断级结论，项目零埋点、零用户访谈，尚未获得证据级支持；② 人日估算按"单人开发 + AI 辅助"口径，未含评审与回归成本，总量约 35 人日；③ 竞品能力数据来自 2026 年 2 月的公开对比，可能与当前版本有差异；④ 所有功能均需在实现后同步扩充现有自检用例（12 项格式化 / 24 项识别 / 粘贴链路 e2e），保持零 WARNING、exit 0 的验收基线。
