四、三个必须先定的前提 + 待你拍板的问题

冲突 A：缩进设置在各格式化器上是「物理不等价」的
下拉框看着简单，但现状是每个格式化器的缩进写死在代码里，而且有一个改不了：
语言 / 格式化器缩进现状能否被下拉控制
JSON / JS / TS / HTML / CSS（Monaco 内置）跟随 Monaco 选项可以
C / C++ / Java（clang-format）Google 风格 = 2 空格可以（有 IndentWidth 参数）
C#（clang-format）Microsoft 风格 = 4 空格可以
Python（Ruff）indent_width: 4可以
Go（gofmt）官方强制 Tab做不到
同时还要先定这个下拉的作用范围：
  • (a) 只管编辑器里按 Tab 的输入——不碰格式化器。约 0.5 人日，语义简单。
  • (b) 同时管格式化输出——要改 4 个格式化器的参数传递，还要向用户解释「为什么 Go 不听话」。约 1.5 人日。
冲突 B：双语文案有两种截然不同的做法，工作量差 2 倍
设计稿里每个控件都画成了「英文 中文」并排。但顶栏又有一个 EN / 中文 切换器，这就产生了歧义：
(a) 双语并显

每个控件同时显示两种文字，切换器闲置或用来自定义顺序。
成本低：只是把文案字符串改掉。
代价：按钮普遍变宽近一倍，工具栏可能放不下（现在已经有 4 个控件 + 2 个提示）。

(b) 按语言切换

点 EN 只显示英文，点中文只显示中文。
成本高：需要一套 i18n 字典 + 组件全部改写成查表。
额外难点：识别子系统的提示是动态拼接的，例如
未发现任何 TypeScript 专有语法，按 JavaScript 处理（模型判为 TypeScript）
这类文案要先改造成「模板 + 参数」才能翻译。

我的建议：走 (b)，但分两期——第一期只覆盖界面控件文案（约 25 条），识别提示与 alert/confirm 弹窗文案放第二期。 理由：截图里明确画了语言切换器，说明你要的是「切换」；(a) 的双语并排会让工具栏拥挤，和设计稿的清爽观感自相矛盾。
另一个建议：不引 i18next 之类的库，用手写词典 + React Context 即可（当前项目无任何状态库，引库会打破「零依赖」的一致性）。

冲突 C：Geist 没有中文字形
Geist 是 Vercel 的开源字体（SIL OFL 1.1，商用免费），但它只有拉丁字母。 设计稿里的「格式化」「历史记录」「就绪」这些中文，浏览器会自动回落到系统默认中文字体—— 结果就是中英文风格割裂（Geist 的 x-height 和字面跟苹方/微软雅黑差得很明显）。
方案效果体积代价
只用 Geist + 系统中文兜底中文部分随系统变（Windows 是雅黑、Mac 是苹方），无法保证设计稿观感0
Geist + 打包思源黑体 / Noto Sans SC完全统一，可控+1~2MB（子集化后）
Geist + 系统中文，但微调字重/字距折中，需要实际渲染对比调0
两个实现注意点：
① 字体文件必须放进项目本地打包，不能引 Google Fonts CDN——项目核心卖点是「离线/内网可用、不依赖外部 CDN」，引 CDN 会自毁卖点。
② Monaco 编辑器不吃 CSS 的 font-family，必须单独传 editor.updateOptions({ fontFamily })，这处很容易漏。

五、建议的实施方式

5.1 先立「设计令牌」，再动界面

现在的颜色是散落在 App.css 各处的字面值（#2196F3 出现 10 次以上）。 直接逐条改色会留下大量漏网的旧蓝。建议第一步先把颜色、圆角、间距、字号抽成 CSS 变量集中在 :root， 再改值——这样换肤是「改 12 个变量」而不是「改 80 处字面值」。 这一步不改变任何外观，是纯粹的准备工作，但能让后面每一步都快。

5.3 两个必须守住的底线

底线一：改完必须补 UI 级自检。 项目现在的自检跑的是「算法对不对」，cdp-selftest.js --only=paste 才勉强算 UI 级。 这次重写顶栏、工具栏、左栏、新增状态栏，属于大面积 DOM 变更， 必须新增：状态栏数值正确性断言、历史徽章与语言一致断言、清空确认后条数为 0 的断言。

底线二：不要在这一批里顺手改功能逻辑。 「历史静默丢数据」「当前内容不落盘」这两个 P0 缺陷还在。 如果一边换肤一边修数据，出问题时无法判断是样式改动还是逻辑改动引起的。 先把 UI 落地，再处理数据缺陷——除非你希望合并做（那样建议重新排期）。
